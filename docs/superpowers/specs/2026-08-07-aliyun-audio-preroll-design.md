# 阿里云首字音频预缓冲设计

> 状态：待评审

## 背景

快捷键呼出面板后，用户已经可以看到界面并开始说话，但阿里云引擎当前仍按以下顺序工作：

1. 检查输入设备并等待 WebSocket 连接；
2. 发送 `run-task`，等待服务端 `task-started`；
3. `task-started` 到达后才启动 `AudioCapture`；
4. 启动采集后才发送 PCM 音频。

因此，用户在第 2 步和第 3 步之间说出的首字没有进入识别链路。面板的显示和真正可以稳定收音之间也存在一个用户不可见的时序窗口。

## 目标

- 阿里云引擎在远程 task 握手期间先接住麦克风 PCM，避免正常启动延迟吞掉首字。
- 服务端 task 就绪后，按采集顺序先补发缓冲音频，再进入实时发送。
- 面板只有在远程 task 已就绪且初始音频已交给发送队列后，才显示“聆听中…”并播放开始提示音。
- 取消、麦克风失败、WebSocket 失败和 task 超时都能丢弃本次缓冲，不产生迟到的音频发送或幽灵 task。
- 不改变当前已经验证的权限、回写、粘贴、引擎切换和历史记录行为。

## 非目标

- 不把这套远程预缓冲套到系统听写或其他本地引擎。
- 不把它做成网络音频缓存、离线录音或跨会话队列。
- 不修改麦克风权限申请策略、辅助功能回写策略或渠道签名策略。
- 不在本次工作中改变音频采样格式；仍按阿里云 task 要求发送单声道 16 kHz PCM。
- 不通过固定延迟（例如无条件等待 300–500 ms）掩盖启动竞态。

## 方案

### 引擎范围

预缓冲只存在于 `AlibabaASREngine`。`SystemDictationEngine` 和 `LegacyDictationEngine` 不创建远程音频队列；它们继续使用自身的本地启动流程，只复用 coordinator 已有的“准备中 / 聆听中 / 失败”状态边界。

### 阿里云启动顺序

阿里云一次录音会按如下顺序运行：

1. coordinator 立即展示面板，状态为“准备中…”。
2. 引擎完成输入设备预检、准备 task 生命周期、安装音频回调，并启动 `AudioCapture`。
3. 音频回调把 PCM 交给一个有上限的本地预缓冲器；此时不向 WebSocket 发送音频。
4. 引擎发送 `run-task` 并等待 `task-started`。
5. 收到当前 task 的 `task-started` 后，发送端原子地从 `buffering` 切换为 `draining`，按 FIFO 顺序将缓冲块加入现有串行发送队列。
6. 缓冲块全部加入发送队列后切换为 `live`；之后到达的 PCM 直接加入同一个发送队列，保持顺序。
7. `start()` 在第 6 步完成后返回，coordinator 才设置“聆听中…”并播放开始提示音。

这里的“完成”指音频已经进入同一个串行发送路径，不等待 ASR 返回文字；识别结果仍然通过现有 WebSocket 接收流程异步更新。

### 预缓冲器契约

预缓冲器应是一个可独立测试的组件，不直接依赖 WebSocket 或 AppKit。它只负责 PCM 数据和生命周期：

- 状态单向变化：`buffering -> draining -> live`，或任意非完成状态 -> `discarded`。
- 按音频块到达顺序保存数据；排空时每个块只消费一次。
- 上限按 PCM 字节数计算，目标容量约为 1 秒的 16 kHz、单声道、16-bit PCM，即约 32 KB；上限应集中定义，不散落在发送代码中。
- 不允许无界增长。超过上限时返回明确的溢出结果并记录日志；不能静默丢掉用户已经说出的音频。引擎应终止这次启动并提示用户重试，而不是制造一个看似成功但缺少首段文字的会话。
- `discarded` 后任何迟到的音频回调都不能发送。
- 排空操作只能执行一次；重复收到 `task-started`、重复恢复 continuation 或迟到的 WebSocket 事件都不能重复发送缓冲。

发送顺序由同一个串行发送队列负责。切换到 `draining`、提交缓冲块、切换到 `live` 和提交后续实时块必须有清晰的串行边界，不能依赖多个并发 Task 的“通常顺序”。

### 失败与取消

- 输入设备预检失败：不创建远程 task，直接走现有恢复面板。
- `AudioCapture.start` 失败：停止本次启动，不保留缓冲，不向服务端发送结束后遗留的音频。
- `run-task` 或 `task-started` 超时：停止采集、丢弃缓冲、结束或标记失败当前 task，并走现有恢复面板。
- 用户在“准备中…”阶段再次按快捷键：取消启动，丢弃缓冲；任何之后到达的 `task-started` 都只能完成清理，不能让会话重新进入录音。
- 录音中麦克风或 WebSocket 失败：沿用现有 `onFailure` 路径；先停止采集和发送，丢弃未发送缓冲，再由 coordinator 展示可操作的恢复提示。
- `stop()` 发生在 `task-started` 尚未到达时：继续使用现有 task 生命周期的 finish 保护，但不发送任何尚未获得 task 资格的音频。

### 用户界面边界

- 面板可以立即出现，但初始文案必须明确是“准备中…”，不能让用户误以为已稳定收音。
- 只有收到服务端 task 就绪且预缓冲已进入发送队列后，才显示“聆听中…”。
- 开始提示音绑定这个真实就绪边界，不再绑定快捷键事件本身。
- 失败信息继续使用现有恢复提示，不在状态文字后追加容易被忽略的小字。

## 并发与生命周期约束

- 预缓冲、发送状态和当前 task ID 必须属于同一会话；新会话不能消费旧会话的数据。
- 关闭、重连或替换 WebSocket 后，旧连接的事件必须通过现有 connection epoch 校验，不能触发当前会话排空缓冲。
- `start()`、`stop()`、`failSession()` 和迟到的 `task-started` 事件必须保持幂等：每个 continuation 至多恢复一次，每个 task 至多发送一次 finish。
- 所有新增状态转换都必须有日志，至少包含 task ID、缓冲块数量、缓冲字节数、排空开始/完成、溢出、丢弃原因；日志不得写入识别文本或 AI 协同元信息。

## 测试策略

### 纯组件测试

- 按 FIFO 追加和排空，验证字节内容、块数量和总字节数。
- 达到容量上限时返回溢出，不发生静默截断。
- 排空只能成功一次；排空后新增数据进入实时路径，不重复消费旧数据。
- 丢弃后追加、排空都不产生可发送数据。

### 引擎生命周期测试

- 在 `task-started` 前收到音频时，音频只进入缓冲，不调用 WebSocket 音频发送。
- `task-started` 后先发送全部缓冲，再发送实时音频。
- `task-started` 重复或旧 task 事件不会重复排空当前缓冲。
- 启动超时、取消、采集失败和 WebSocket 失败都会停止采集并丢弃缓冲。
- coordinator 只有在引擎启动成功后才进入 `recording`，不会因为面板已展示就提前播放开始提示音。

### 回归验证

- 保留现有 23 个单元测试并新增预缓冲和生命周期测试。
- 构建 App Store 渠道 archive，验证签名和可运行性。
- 真机重点场景：快捷键后立即说话、连续多次启动、准备阶段再次按快捷键、无麦克风、切换蓝牙耳机、切换本地/阿里云引擎。
- 重点观察首字完整性、开始提示音、失败恢复、历史记录和回写，不以单次“能识别”作为唯一通过标准。

## 验收标准

1. 阿里云 task 正在握手时立即说出的内容，在 task 正常就绪的情况下能够按顺序进入识别。
2. 本地引擎行为不因该改动改变。
3. 启动失败或取消后没有迟到音频、幽灵 task 或下一次会话污染。
4. 面板状态与实际可收音状态一致，开始提示音不会早于真实就绪。
5. 测试、App Store archive 构建和三台真机回归均通过后，才将这项优化视为完成。
